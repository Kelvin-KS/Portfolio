Method

One plan, two ways of running it

The same 41 test cases, each with steps and an expected result, were run by automation on emulated devices and by hand on real ones. Every result says which it was.

The plan

41 test cases across 10 areas: navigation, theme, the hero, the QA Lab, contact and CV, accessibility and performance. Each case is marked every device, laptop only or once is enough, so effort goes where the risk is.

AI-assisted automated checks

I directed an AI assistant to script my test cases against the live site in Chrome's device mode: 6 emulated phones and tablet plus desktop Chrome. Each check follows the steps and compares actual with expected. It covered screen sizes, dark mode, rotation, large text, reduce-motion and a slow 4G connection.

By hand, on real devices

What automation can't do honestly: the clipboard, the phone's mail app, the real system font setting, Lighthouse, link previews in WhatsApp and LinkedIn, and signed-in links. Done on a real Galaxy A32 (Chrome) and my laptop.

Known limits

Emulation runs Chrome's engine, so it is not a real Safari or Samsung Internet test. A real iPhone Safari run is still pending and will be added to this page.

Issues found & fixed

14 bugs caught before a visitor could

Every issue was caught by my test process: automated checks (AI-assisted) for breadth across devices, and manual checks for what automation misses. Each card says which method caught it, and each follows the same cycle: found, documented, fixed, retested. The fail stays on record rather than being quietly overwritten.

F-01Fixed & retested

Live site hidden behind a Netlify login

Found
Every visitor got 401 Unauthorized and a login page.
Cause
New Netlify projects default to private visitor access.
Fix
Production set to public; deploy previews kept private.
Retest
Live site returns 200 to anonymous visitors.

How it was found: Automated check (AI-assisted)

F-02Fixed & retested

Console errors from an injected Netlify script

Found
2 red Content-Security-Policy errors in the console on every page load.
Cause
Netlify's "Powered by Netlify" badge injects inline code, which the site's security policy correctly blocks.
Fix
Badge turned off (security policy kept strict).
Retest
Zero console errors on the live site.

How it was found: Automated check (AI-assisted)

F-03Fixed & retested

Loading screen could cover the whole page

Found
In a full-page render the KS loading screen never cleared.
Cause
It relied only on a CSS animation to hide itself.
Fix
Two independent timer failsafes remove it after 1.6 s and 2.5 s.
Retest
Clears on every load.

How it was found: Automated check (AI-assisted)

F-04Fixed & retested

Stats showed "0+"

Shows 10+, 10+, 30+, 8+.

F-13Fixed & retested

Menu button pushed off-screen with large text

Found
With the phone font size increased (130%), the header on ~412px-wide phones (Galaxy A15, A32) overflowed: the Menu button ended at 432px on a 412px screen, so it could not be tapped. Also failed on 320px screens.
Cause
Brand text, the labelled theme button and the Menu button did not fit on one line once text scaled up; '/ portfolio' was only hidden below 400px.
Fix
Under 520px the theme button becomes icon-only (full name kept for screen readers) and '/ portfolio' is hidden.
Retest
Deployed and retested on the live site at 320, 360 and 412px with 130% and 150% text: Menu fully on screen every time. TC-36 now passes on Galaxy A15 and A32 (emulated); regression run on S22, iPhone 13 and A15 found no new failures. Confirmed by Kelvin on a real Galaxy A32 with the system font at maximum.

How it was found: Automated check (AI-assisted)

F-14Fixed & retested

Scroll fade-in timing different on the test report page

Found
Comparing the homepage and the test report on laptop and phone, the fade-in on the report felt later and inconsistent. Measured: a ~500px element with its top 20% into the screen had started fading on the homepage but not on the report.
Cause
The report's helper used 'threshold || 0.2'. In JavaScript 0 counts as empty, so the intended threshold of 0 became 0.2 and tall elements (device table, issue cards) waited until 20% of their height was visible.
Fix
Only fall back to 0.2 when no threshold is given, so 0 is respected.
Retest
Same measurement on the live site: the report's device table now starts fading at the same point as on the homepage. Zero console errors.

How it was found: Manual check: visual comparison across pages and devices

Lessons

What this round taught me

  1. Question a bad result before "fixing" the site

    Lighthouse first scored Performance 63. It named browser extensions as the cause. Re-run in a clean Incognito window: 98. Nothing needed changing.

  2. Automation can be wrong too

    The automated run reported four failures that turned out to be mistakes in the test script (a hidden spam-trap field, reading a result too early, a desktop touch setting and where keyboard focus started). Each was investigated and re-run before anything was recorded; none are counted as site bugs.

  3. Emulation is not a real phone

    Copying to the clipboard and opening the mail app could only be proven on a real Galaxy A32. That's also why a real iPhone Safari run is still on the list.

  4. Eyes catch what checks don't

    Every automated check passed, yet the fade-in felt later on this page than on the homepage. I noticed it by comparing the two by eye; measuring confirmed it (F-14). Automation checks what you tell it to. Manual QA notices what nobody wrote down.

  5. Bugs live at the edges

    F-13 only appeared with a large system font on mid-width phones. Normal settings never showed it. It was found, fixed, retested at three screen sizes, regression-tested, then confirmed on a real phone at maximum font size.
